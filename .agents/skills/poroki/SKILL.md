# Пороки — когнитивная алхимия для ревью и исправления кода

Задача: изменить ход инженерного мышления, а не просто формат отчёта. Используй навык для любого репозитория, особенно World Server. Если пользователь просит «проверь скилом Пороки», проводи ревью и, когда разрешён доступ на запись и нет запрета на исправления, исправляй воспроизводимые дефекты. При явном READ-ONLY не изменяй файлы, ветки и настройки.

## Семь превращений

1. **Лень → автоматизация.** Не избегай трудной проблемы: напиши воспроизводимый тест, диагностику или скрипт, чтобы больше не решать её вручную. Сначала проверь существующие инструменты, не изобретай дубликаты.
2. **Гордыня → опровержение.** Сформулируй гипотезу об исправности кода и активно ищи контрпример. Не принимай собственный патч за доказательство. По возможности привлекай независимого рецензента, проверяй его замечания воспроизведением.
3. **Жадность → инженерная эффективность.** Ищи один корневой дефект, объясняющий несколько симптомов; предпочитай минимальный проверяемый патч. Не жертвуй корректностью ради скорости или экономии.
4. **Страх → моделирование отказов.** Проверяй неверный ввод, потерю сети, конкурентные запросы, двойные события, таймауты, повторные попытки, сохранность данных и возможность отката.
5. **Зависть → изучение эталонов.** Сверяй архитектуру и тесты с подходящими проверенными решениями; проверяй совместимость и лицензии, не копируй чужой код без разрешения.
6. **Гнев → поиск первопричины.** Не маскируй симптомы и не отключай проверки. Составь цепочку: действие пользователя → вход → состояние → побочный эффект → наблюдаемый сбой.
7. **Нетерпение → короткие циклы обратной связи.** Сначала минимальное воспроизведение и один сквозной пользовательский сценарий, затем узкий патч, затем полный регрессионный прогон. Не пропускай release gates.

## Обязательный цикл

1. **Установи реальность.** Открой актуальный код, инструкции репозитория, тесты, CI и историю вокруг дефекта. Зафиксируй путь, текущую ветку, exact HEAD SHA, status и целевой base. Никогда не считай старый SHA текущим.
2. **Сохрани чужую работу.** При dirty worktree создай изолированный worktree вне рабочего каталога или работай через отдельную ветку/API. Не стирай и не коммить чужие незавершённые файлы.
3. **Собери карту риска.** Для изменённого кода проверь контракт, вызовы, обработку ошибок, права доступа, ввод, данные, конкуренцию, производительность, совместимость и тестируемость. Для игровых движков отдельно проверь детерминизм по seed, границы tick, persist/restore и видимое изменение мира.
4. **Атакуй предположения.** Для каждой важной гипотезы придумай контрпример и реальный пользовательский сценарий. Отделяй подтверждённые дефекты от статических подозрений.
5. **Автоматизируй сигнал.** Запусти scripts/poroki_audit.py с параметрами репозитория как предварительный эвристический анализ. Он не заменяет AST-линтер, тесты, профилирование и ручное чтение кода.
6. **Докажи и исправь.** Для каждого воспроизводимого дефекта сначала получи падающий тест либо минимальное доказательство сбоя; затем реализуй минимальный фикс, регрессионный тест и релевантные проверки. При READ-ONLY приведи проверяемый патч-план без записи.
7. **Попытайся сломать исправление.** Запусти unit/integration/e2e, негативные сценарии и независимое ревью, если доступно. Не превращай skipped, flakey или недоступные проверки в PASS.
8. **Проверь пользовательскую заметность.** При UI-изменениях смотри на реальный браузер и, если применимо, мобильный экран: отображаются ли действия и их последствия. Уровень готовности вычисляй только по заранее указанному проверяемому чек-листу, не придумывай проценты.
9. **Отчёт = доказательства.** Укажи подтверждённые дефекты с файлом, местом, входным сценарием и эффектом; внесённые правки; команды и результаты тестов; exact SHA патча/PR; непроверенное и оставшиеся блокеры. Если записи или тесты недоступны, скажи это прямо.

## Особые правила World Server

- Соблюдай имеющиеся ограничения проекта на размер файлов, методов и imports; если они реально действуют, проверь значения 400 строк, 50 строк на метод и 10 imports с подходящим AST-инструментом. Эвристический скрипт проверяет только файлы/imports.
- Проверяй полный цикл «размещение → намерение → выбор Джинна → детерминированные последствия → видимая анимация → сохранение → продолжение», включая desktop и mobile.
- Не обходи quality gates, не считай skipped тест пройденным, не публикуй игровую тестовую ссылку до подтверждённого пользовательского порога заметности >85%.
- Не создавай шестую автоматизацию АКА для интеграции этого ревью: переиспользуй существующий процесс, если пользователь отдельно попросит автоматизировать выполнение.

## Безопасность и границы

Не печатай токены, значения .env, приватные данные или полные фрагменты с секретами. Не запускай опасные команды, массовое удаление, merge, production deploy либо секретные изменения без явного разрешения. Не обещай фоновую работу без реально созданной автоматизации.
