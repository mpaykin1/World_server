# Procedural Krieger MVP — успешный паттерн управления и графического отклика

**Дата фиксации:** 30 сентября 2026  
**Статус:** USER-CONFIRMED SUCCESS  
**Канонический исходник в World Server:** `apps/chain-reaction-procedural-krieger/index.html`  
**Источник:** пользовательский автономный HTML «Цепочка — Procedural Krieger World»

Этот документ фиксирует следующий успешный этап после Meta4. Пользователь отдельно отметил две вещи, которые необходимо сохранить и переиспользовать:

1. **по пространству игры удобно двигаться**;
2. **при строительстве появляются заметные графические элементы**.

Цель handoff — чтобы следующий чат или агент не переписывал этот опыт заново, а мог взять работающие приёмы как базовый UX/graphics pattern для World Server.

## 1. Что именно оказалось удачным

### 1.1. Перемещение воспринимается как управление миром

В MVP игровая поверхность — полноэкранный fixed canvas с `touch-action:none`. Камера хранится отдельно:

    cam = { x, y, zoom }

и есть симметричные преобразования:

    w2s(worldX, worldY)
    s2w(screenX, screenY)

Одним пальцем игрок панорамирует мир, двумя — меняет масштаб. При pinch world-point под центром жеста сохраняется через преобразование «до/после» изменения zoom. На desktop тот же принцип работает для wheel zoom.

Это важный UX-успех: управление ощущается как самостоятельное перемещение по игровому пространству, а не как прокрутка HTML-страницы.

## 2. Почему pan удобный

В коде одновременно работают несколько небольших решений:

- `setPointerCapture(pointerId)` не теряет активный жест;
- все активные pointer хранятся в `Map`;
- есть порог движения около 5 px, отделяющий tap от drag;
- camera pan делится на текущий zoom;
- pinch использует расстояние между двумя pointer;
- zoom ограничен диапазоном, чтобы мир не исчезал и не раздувался бесконечно;
- после zoom камера компенсируется так, чтобы точка под пальцами оставалась на месте.

Ключевой переносимый принцип:

> Tap, pan и pinch должны быть разными состояниями одного input-controller, а не тремя независимыми обработчиками, спорящими за один жест.

## 3. Почему бесконечное пространство остаётся визуально живым

Фон не является одной большой картинкой.

`drawGround()` каждый кадр:

1. переводит края текущего экрана через `s2w()` в мировые координаты;
2. вычисляет диапазон видимых procedural cells;
3. рисует только клетки вокруг текущего viewport;
4. использует seed/hash для стабильных деталей местности.

Поэтому игрок может двигаться далеко, а пространство продолжает порождать визуальную структуру без огромной заранее созданной карты.

Это хороший паттерн для World Server:

    camera viewport
    -> visible world bounds
    -> visible chunks/cells
    -> deterministic procedural render

## 4. Второй пользовательский успех: объекты действительно выглядят как объекты

Этот MVP важен тем, что действие игрока не заканчивается изменением цифр.

Для шести базовых типов есть отдельные procedural renderers:

- город;
- лес;
- вулкан;
- электростанция;
- ферма;
- река.

Используются простые переиспользуемые графические примитивы:

- `box()` — псевдоизометрический объём;
- `cyl()` — цилиндрические сооружения;
- `ellipseGround()` — тень/основание;
- `poly()`, `line()`, `tri()`;
- `glow()` — свет;
- `smoke()` — анимированный дым.

На их основе появляются визуально различимые композиции: здания и окна города, деревья, слои вулкана и лава, градирня/трубы станции, поля/дом/мельница фермы, русло воды и камни.

### Почему это важно

В World Server нельзя считать действие реализованным, если изменились только числа интерфейса.

Минимальный успешный feedback loop:

    действие
    -> world-space объект
    -> заметный графический объект
    -> анимация/свет/деталь
    -> изменение игрового состояния

## 5. Точный placement после исследования мира

Пользователь сначала выбирает инструмент, затем может сколько угодно двигать мир.

Строительство не срабатывает во время drag, потому что tap отделён порогом `moved`.

Только короткий tap после выбора инструмента:

    screen tap
    -> s2w(tap.x, tap.y)
    -> pending world coordinates
    -> forecast modal
    -> YES
    -> apply(kind, worldX, worldY)

Таким образом объект создаётся именно там, куда игрок указывает в текущем видимом пространстве.

Этот паттерн нужно сохранять вместе с ранее зафиксированным viewport-local placement contract.

## 6. Визуальный слой дешёвый и автономный

MVP не требует внешних GLB/PNG/texture assets для базовых объектов. Геометрия собирается непосредственно Canvas 2D-командами.

Преимущества для быстрых World Server прототипов:

- автономный один HTML;
- быстрый старт на телефоне;
- отсутствие загрузки тяжёлых моделей;
- procedural variation через seed;
- легко создавать десятки новых типов из одних и тех же примитивов;
- визуальный feedback появляется сразу после добавления нового object renderer.

Этот подход полезен как **low-cost procedural visual lane**, даже если production-версия позже перейдёт на WebGL/Three.js/GLB.

## 7. Что нужно переиспользовать как модуль

При дальнейшей разработке не копировать весь HTML вручную. Выделять и переиспользовать следующие абстракции:

### CameraController
- `cam.x / cam.y / cam.zoom`;
- `w2s / s2w`;
- pointer map;
- tap/drag threshold;
- pinch anchored zoom;
- wheel anchored zoom.

### VisibleChunkRenderer
- определение world bounds текущего viewport;
- deterministic hash/seed;
- отрисовка только видимых cells.

### ProceduralPrimitiveRenderer
- box;
- cylinder;
- polygon;
- line;
- ground ellipse;
- glow;
- smoke.

### ObjectRendererRegistry
- kind -> renderer;
- каждый игровой объект имеет world-space `x/y`, kind, scale/id;
- renderer решает только визуализацию, а не игровую логику.

### PlacementController
- selected tool;
- tap -> world position;
- pending action;
- forecast;
- YES/NO;
- только YES создаёт объект.

## 10. Regression rules

Следующие свойства теперь считаются пользовательски подтверждёнными и не должны теряться:

1. drag одним пальцем легко перемещает мир;
2. pinch меняет масштаб без скачка world-point под пальцами;
3. tap не путается с drag;
4. после pan/tap объект возникает ровно в указанной области;
5. фон продолжает генерироваться после дальнего pan;
6. графические объекты различимы по типу без чтения подписи;
7. анимированные детали продолжают работать во время перемещения камеры;
8. HUD остаётся отдельно от world-space;
9. базовый прототип остаётся автономным и лёгким;
10. дальнейшая интеграция AI/симулятора не имеет права ухудшить пункты 1–8.
