# Meta5 — пользовательский разбор успехов и двух неудач

**Дата:** 30 сентября 2026  
**Основание:** пользовательская проверка живой Meta5  
**Живая версия:** https://mpaykin1.github.io/meta5/  
**Meta5 commit, на котором получен feedback:** `eecb8d6b368760e5a01b61bac114be4aceedf1ae`  
**World Server AI merge:** `284dc4eba8d127b218ae7998a05a4bafc156a151`

Этот документ дополняет `docs/META5_LIVE_AI_MERGE_SUCCESS_2026-09-30.md` и фиксирует реальный пользовательский feedback после использования MVP.

## 1. Итог пользователя

Пользователь оценил Meta5 положительно и отдельно сообщил:

**Успех:** «Всё остальное успех. Всё работает супер».

**Неудача 1:** кнопка **«Идея»** не работает — по пользовательскому наблюдению она «просто не нажимается».

**Неудача 2:** использованная карточка остаётся отключённой. Пользователь ожидает, что **сразу после подтверждённого действия на её месте появляется новая кнопка** — следующая логическая постройка или развитие.

Эти два дефекта не отменяют уже подтверждённые успехи camera/input, glyph UI, procedural graphics, live AI, exact placement и local report.

## 2. Что в Meta5 следует считать подтверждённым успехом

Следующие свойства не должны быть переписаны или ухудшены при исправлении дефектов:

1. удобное перемещение по пространству одним пальцем;
2. pinch-to-zoom;
3. world-space/screen-space преобразования;
4. точный tap-to-place;
5. система иероглифов как компактный язык действий;
6. после подтверждения возникает графический объект, а над ним остаётся маленький иероглиф;
7. процедурная анимация объектов;
8. живой World Server AI вместо заранее написанного прогноза;
9. AI остаётся prediction-only и возвращает `executed:false`;
10. `NO` не изменяет мир;
11. `YES` создаёт один объект;
12. жители/ресурсы/локальный отчёт реагируют после подтверждения;
13. Meta4 остаётся отдельной неизменяемой regression baseline.

При будущих исправлениях нельзя лечить две найденные ошибки переписыванием этих уже работающих частей.

## 3. Неудача №1 — «Идея» не нажимается

### Пользовательский симптом

В первой пятёрке действий присутствует:

    人 Идея

На реальном пользовательском устройстве эта кнопка не проходит ожидаемую цепочку взаимодействия.

### Что показывает исходный код

У `idea` нет отдельного button-handler. Она создаётся тем же общим кодом `renderDeck()`, что город, лес, вулкан и энергия:

    b.onclick = () => selectAction(a.id, b)

То есть статически кнопка не забыта и не отключена специальным условием.

`idea` присутствует в каталоге:

    { id:'idea', name:'Идея', glyph:'人', ... }

Для неё также существует отдельный renderer:

    drawIdea(o)

и dispatch:

    else if (o.k === 'idea') drawIdea(o)

### Проверка backend

Проверен production endpoint:

    POST /api/chain-ai
    mode: predict_action
    action.kind: idea

Он **не отвергает** действие `idea`.

Фактический smoke 30 сентября:

- HTTP 200;
- provider: Cloudflare;
- `executed:false`;
- ответ получен примерно за 11.7 секунды.

Следовательно, подтверждённая пользовательская проблема **не является отсутствием `idea` в server allowlist**.

### Что пока НЕ доказано

Точная причина «не нажимается» на физическом устройстве пока не воспроизведена.

Нельзя писать в будущем handoff, будто причина уже известна.

Возможные классы причины, которые требуется проверить, а не принять как факт:

- touch/click delivery к крайней правой карточке на физическом iPhone;
- потеря состояния между button tap и следующим canvas tap;
- визуально незаметное состояние selected;
- длительный AI-response, который пользователь воспринимает как отсутствие реакции;
- browser/webview-specific event behavior.

### Важное наблюдение о latency

Для `idea` production smoke в этот раз занял около **11.7 s**, тогда как предыдущий `river` smoke через Groq был около 0.76 s.

Это не доказывает причину bug, но создаёт UX-риск: даже правильно выбранная кнопка может восприниматься как «не работает», если после canvas tap долго нет понятного feedback.

### Обязательный regression test перед закрытием дефекта

Проверить на физическом iPhone:

    tap 人 Идея
    -> action получает active state
    -> message меняется на "人 Идея..."
    -> tap в playable world
    -> modal открывается немедленно
    -> loading-state виден немедленно
    -> AI request уходит
    -> либо live prediction, либо честный Retry
    -> YES строит один Idea-object
    -> над объектом виден 人

Отдельно логировать timestamps:

    button pointerdown
    button click
    selected=idea
    canvas pointerdown
    canvas pointerup
    modal shown
    request started
    response/error received

Без этого нельзя объявлять bug исправленным.

## 4. Неудача №2 — использованные кнопки не заменяются сразу

### Пользовательский ожидаемый UX

После того как действие подтверждено и объект построен, использованная карточка должна **сразу исчезнуть/замениться**, а на её месте должна появиться:

- следующая логическая постройка;
- или следующее логическое развитие мира.

Остальные четыре доступные карточки при этом должны оставаться.

### Точная причина найдена в коде

Это не случайный UI-баг. Текущая логика Meta5 специально работает пакетами по пять.

После YES выполняется:

    pendingButton.disabled = true
    S.used.add(pending.k)

а новая партия появляется только при:

    if (S.used.size === 5)
        setTimeout(nextDeck, 230)

Функция `nextDeck()` затем увеличивает `S.batch` и полностью перерисовывает пятёрку.

Следовательно, текущая реализация означает:

> использовать все пять -> только потом получить следующие пять

а пользователь требует:

> использовать одну -> немедленно получить одну новую логическую карточку в освободившемся слоте

Это подтверждённая архитектурная ошибка относительно желаемого игрового loop.

## 5. Правильный новый contract для action deck

Deck должен стать **не batch deck, а continuously replenished deck**.

Обязательное поведение:

    5 active cards
    -> player confirms one card
    -> exactly that slot becomes vacant
    -> world mutates
    -> successor selection runs
    -> one new card fills that same slot
    -> again 5 active cards

Не ждать использования остальных четырёх.

## 6. Что значит «следующая логическая постройка или развитие»

Нельзя исправить дефект только циклическим:

    city -> catalog[5]
    forest -> catalog[6]
    ...

Это технически обновит кнопку, но не выполнит смысл запроса пользователя.

Нужен successor layer, который выбирает действие по контексту.

Минимальный deterministic вариант может использовать:

- действие, которое только что выполнено;
- локально видимые объекты;
- текущие ресурсы;
- дефициты;
- уже предложенные/использованные действия;
- spatial synergies.

Примеры логических переходов:

    Город -> Дом / Рынок / Школа / Дорога / Энергия
    Лес -> Вода / Сад / Река
    Энергия -> Мастерская / Город / Освещение/развитие
    Ферма -> Вода / Рынок / Дорога
    Река -> Мост / Ферма / Город
    Вулкан -> Энергия / Вода / Дорога/эвакуация
    Идея -> Школа / Община / Мастерская

Позже этот selector может получить AI-assisted ranking, но сама игра не должна блокироваться, если AI недоступен.

## 7. Рекомендуемая архитектура исправления deck

Вместо `batch + used.size===5`:

    slots[5]
    nextCandidateIndex / successor selector
    usedHistory
    offeredHistory

После YES:

1. сохранить `consumedKind`;
2. найти индекс использованной кнопки;
3. вычислить `successor = chooseSuccessor(consumedKind, worldContext)`;
4. заменить только этот slot;
5. создать новый DOM button или обновить существующий;
6. новая карточка сразу clickable;
7. остальные четыре slot не менять.

Важный invariant:

    deck always has 5 usable logical choices
    except while one slot is in transient replacement animation

## 8. Не делать следующие ошибочные исправления

### Не перерисовывать весь интерфейс после каждого хода

Это может сбросить selected state, touch state и создать новую мобильную регрессию.

### Не возвращать использованную карточку сразу

Иначе игрок будет нажимать один и тот же выгодный action бесконечно.

### Не давать AI право непосредственно менять deck/world

AI может предложить/rank successors, но authoritative client/game logic решает, какая карточка реально становится доступной.

### Не скрывать latency «фальшивым прогнозом»

Meta5 специально отказалась от заранее написанных forecast. Если provider медленный — показывать loading/progress/retry, но не подменять ответ локальной заготовкой.

### Не считать Idea bug закрытым только потому, что backend отвечает

Пользовательский bug находится в end-to-end interaction path. Нужен именно физический touch proof.

## 9. Новые обязательные regression checks

Перед следующей публикацией Meta5:

1. `Идея` нажимается на физическом iPhone.
2. После нажатия `Идея` active state визуально заметен.
3. После world tap modal появляется до завершения AI request.
4. Idea live prediction либо приходит, либо появляется Retry — UI никогда не выглядит мёртвым.
5. YES создаёт ровно один Idea-object.
6. Над Idea-object виден `人`.
7. После любого успешного действия использованный slot заменяется сразу.
8. Через 10 последовательных действий deck всё время содержит 5 доступных логических choices.
9. Замена одного slot не меняет остальные четыре.
10. NO не расходует карточку и не заменяет её.
11. AI failure не расходует карточку.
12. pan/pinch/tap, graphics, glyph labels и local report не регрессируют.

## 10. Приоритет следующего исправления

Не строить новую Meta6.

Исправлять существующую Meta5 минимально:

**P0**
- reproduce/fix Idea touch path;
- continuous per-slot deck replenishment.

**P1**
- context-aware successor selection;
- immediate visual feedback after every card tap;
- explicit AI loading timer/status.

**Не трогать**
- camera model;
- world/screen transforms;
- procedural renderers;
- small glyph labels;
- live AI `predict_action`;
- NO/YES mutation gate;
- Meta4 baseline.

## 11. Главный урок

Meta5 уже доказала, что:

**glyph -> spatial choice -> live AI -> confirmation -> animated graphical consequence**

работает и нравится пользователю.

Но action deck — это часть core loop, а не декоративный UI.

Если использованная карточка остаётся мёртвой до конца партии из пяти, ощущение развития мира ломается.

Новый canonical loop должен быть:

**5 живых вариантов -> 1 выбор -> 1 последствие -> 1 новый логический вариант -> снова 5 живых вариантов.**

А bug `Идея` необходимо лечить как end-to-end mobile interaction defect, а не как проблему AI allowlist.
