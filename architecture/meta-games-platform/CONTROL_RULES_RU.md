## 2. Цикл контроля

1. Прочитать последний checkpoint, статус исполнителя, последнее назначение и его результат.
2. Проверить GitHub: текущие base/HEAD SHA, изменения файлов, занятые ветки, PR, свежие CI и ревью. Перед редактированием повторно проверить владение и SHA.
3. При активной работе не прерывать исполнителя, не дублировать задание. Передавать уточнение только при новых существенных данных.
4. При завершённом результате проверить фактическое поведение и доказательства на соответствующем SHA.
5. При ошибке назначить конкретное исправление с воспроизведением и регрессией. Не повторять детерминированно проваленный запуск без изменения причины.
6. Если исполнитель свободен, выдать одно следующее незанятое задание с критериями приёмки и запустить выполнение. При внешнем блокере выбрать независимую доступную работу.
7. Проверить доставку и статус запуска, сохранить checkpoint. Не выдавать отправку сообщения за выполнение задания.
8. Продолжать до подтверждения всех критериев завершения; при остановке владельцем прекратить цикл.

Если read_thread возвращает только ссылки content-reference вместо ответа, содержание неизвестно: сверять GitHub, а не придумывать отчёт исполнителя. Если инструменты недоступны, фиксировать конкретный предел наблюдения. idle без нового результата не означает успех, active означает активный чат, а не доказанные изменения кода.

## 4. Что считается доказательством

## 9. Проверяемая готовность вместо оценок на глаз

Применяется к отчётам MCP, библиотеки решений, бота и всей фабрики. Числа «75% / 60% / 50% / всего 62%» без проверяемого расчёта не являются метрикой. Среднее трёх оценок не доказывает готовность продукта.

1. До расчёта зафиксировать область, версию требований, список критериев и веса; не менять знаменатель после результата. Если этого нет, писать «процент не определён», а не придумывать новое число.
2. Для каждого критерия: PASS / FAIL / UNKNOWN / BLOCKED; репозиторий, точный SHA, PR, workflow/job, проверенное поведение, среда, дата и следующая операция. UNKNOWN не является дефектом, но не засчитывается как PASS. BLOCKED не закрывает критерий.
3. Отдельно показывать код-кандидат, интеграцию в основную ветку и публичную проверку. Результаты sandbox/stdio не засчитывать как публичный HTTPS MCP или готовый production.
4. Для фиксированной проверочной матрицы допустимо считать долю подтверждённых критериев: сумма весов PASS / сумма всех весов. Называть её именно покрытием проверки, не вероятностью успеха и не процентом готового кода. Изменение области требует новой версии и объяснения.
5. RELEASE READY — логическое «И» всех обязательных критериев. Среднее не компенсирует провал прав, безопасности, полного прохождения, обязательного CI или публикации. Художественный OWNER PASS — только по словам владельца.
6. Для библиотеки раздельно считать найденные файлы, очищенные по правам компоненты, извлечённые versioned API и компоненты, реально использованные второй игрой. Индекс файлов и поиск не доказывают готовую библиотеку.
7. Для бота раздельно считать игры с полным прохождением, стабильность повторов и успешно исправленные реальные дефекты. BOT_ALREADY_PASS доказывает только исходный PASS; не доказывает автоисправление. Требуется FAIL до патча → минимальный патч → тот же сценарий PASS → полный desktop/mobile/повторный заход; неуспешный патч должен откатываться.
8. Генератору требуются разрешённые доноры и зависимости с закреплёнными source SHA/хешами, трасса стадий, настоящий браузерный ввод и разрешённая публикация. Новая процедурная сцена, сборочный integrity PASS или preview сами по себе не закрывают создание допущенной игры.

- Один ответственный и одно активное исправление на компонент. При конкурирующих PR явно указать основной PR и зависимость/замену; не закрывать и не перезаписывать чужой PR автоматически. Независимая работа допустима только по непересекающимся файлам/контрактам.
- У каждой задачи одна проверяемая причина, ограничение файлов, критерий завершения и NEXT_ACTION. Не открывать новую функцию, пока доступно закрытие текущего технического хвоста. Соблюдать существующий tail budget AGENTS §20a.
- Сначала воспроизвести дефект с seed/вводом/средой, затем минимальное исправление. Проверять испорченный сценарий и обратные случаи; общую библиотеку — также во всех затронутых потребителях. Защищённые bot core, оригиналы и пороги не менять ради зелёного статуса.
- Повторный запуск разрешён при новом патче, доказанной временной ошибке среды или существенном изменении условий. Исчерпание бесплатной квоты не лечить одинаковыми повторами, оплатой или неразрешённой сменой провайдера. Указывать причину каждой повторной попытки.
- SUCCESS workflow интерпретировать по job/логам: skipped, cancelled, отсутствие выбранных игр, отсутствие подходящего исправления и BOT_ALREADY_PASS не выдавать за выполненный ремонт. Для отрицательного результата — понятная причина и ссылка на job в PR/сводке; не удалять провалы.
- После каждого push обновлять описание PR и соответствующую существующую карточку: полные SHA, последний run, PASS/FAIL/UNKNOWN и причина. Ссылки на движущуюся main не заменяют закреплённый источник. Состояние «выполняется» обновлять по API, а не сохранять сутками.
- При опросе сравнивать SHA, новый результат, блокер и NEXT_ACTION. Если ничего не изменилось, обновление времени не считать продвижением и не создавать дубли заданий. Если чат остаётся reference-only без работающего канала, не накапливать сообщения: проверять GitHub и выполнять допустимую независимую работу либо фиксировать конкретный внешний блокер.
- После merge проверить deployment и фактический deployed SHA/manifest. HTTP 200, публикация страницы и прохождение игры — отдельные критерии. При недоступности сети фиксировать UNKNOWN и последнее успешное доказательство с датой, не объявлять свежий live PASS.
- Перед выпуском читать актуальную политику платформы. В meta6 с 07.11.2026 META GAMES-версии без рекламы по rules/09-platforma/BEZ_REKLAMY.md; рекламный адаптер проверяется только в отдельных Playgama-версиях. Это не разрешает менять принятые оригиналы или чужую текущую работу.

Краткий формат результата: «критерий | состояние | repo@SHA | PR/run/job | что проверено | ограничение | следующий шаг». Хранить его в описании/комментарии PR и существующей очереди.
