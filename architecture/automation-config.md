## 2. Жёсткие правила
- Ровно пять задач, новых не создавать. Один `cycle_id` и один PR на цикл.
- Каждая задача, меняющая `stage_completed`, в том же коммите переписывает `notes` одной строкой: этап, head SHA, блокер, следующий шаг.
- Нельзя: фиктивные PASS, пустые коммиты, handoff/evidence/отчётные файлы, новые тест-файлы (проверки — внутри кода, assert в скриптах).
- `remaining = 0` при `verified < applicable` — это FAIL «fake-complete». Каталог не засчитывает сам себя как интеграцию.
- Не трогать `**/stand/**`, `**/accepted/**`, V5–V7, `reference/sumerek-golden/`, принятые игры. Приватные репозитории — только общее число, без имён, путей и кода.
- В играх: только графика и иконки на экране, всё остальное в меню ☰ справа сверху.
- Нет `gh` — использовать GitHub API/коннектор. Платные API не подключать.
- Уведомлять владельца только ссылкой на проверенную играбельную страницу или при 100%.

## 5. Ревью Claude
- **Ревью Claude НЕ является условием для проверки, слияния или продолжения работы.** Независимый проверяющий — задача :40. Ждать Claude запрещено: если новых записей нет, задачи работают дальше по очереди.
- Ревью Claude приходит только в файл `architecture/claude-automation-review.md` (не в комментарии PR), раз в 2 дня. Отсутствие ревью = «замечаний нет».
- Если ревью пришло после слияния — исправления делаются следующим PR, слитое не откатывается без причины.
- :05 каждый час читает `architecture/claude-automation-review.md`, берёт записи со статусом NEW.
- Сверяет с реальным кодом. Верно — выполняет и ставит `APPLIED` + SHA. Неверно — `REJECTED` + причина одной строкой. Нужен доступ, которого нет — `BLOCKED` + чего не хватает.
- Обработанные записи не применять повторно. Историю не удалять.
- Решения о качестве игр (PASS/FAIL) ставит только владелец.
- Claude проверяет работу раз в 2 дня и дописывает новые записи в тот же файл.

## 6. Один планировщик для двух репозиториев (01.11.2026)

Назначение определяется без дополнительного сервиса: `workflow.next_focus` в `architecture/reuse-state.json` имеет одноразовый приоритет до подтверждённого выпуска; иначе по локальному часу Asia/Tbilisi: час % 4 = 0 → GAME_ASH, 1 или 3 → REUSE, 2 → GAME_ABYSS. ## 7. Проверка и доступные инструменты

:40 сверяет **текущий точный SHA PR**. Для Node-каталога допускаются успешно завершённые GitHub Actions `npm run check` на этом SHA (включает `scripts/check-js.js` и `scripts/check-architecture-limits.cjs`) вместе с независимым выполнением `projectsFromTree()` на реальных SHA деревьев через GitHub API и точной проверкой `remaining`; метод проверки фиксируется в существующем `reuse-state.json`. Если проверка не выполнена, статус только BLOCKED или VERIFY_FAIL с причиной. Для игр обязательна проверка реального кадра, управления и загрузки; серверные CI не заменяют браузерную проверку. Новые test/evidence/handoff/report файлы запрещены. Ни Claude, ни его одобрение, ни отсутствие новых заметок не блокируют :40/:50. :50 сливает ровно проверенный SHA, не выдаёт непроверенную ссылку.
