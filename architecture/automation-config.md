## 2. Жёсткие правила
- Ровно пять задач, новых не создавать. Один `cycle_id` и один PR на цикл.
- Единственный источник текстового следа цикла — `workflow.notes` (корневого `notes` нет): этап, head SHA, блокер, следующий шаг. Каждый запуск обязательно обновляет корневой `last_run` в `architecture/reuse-state.json` (`stage`, `time_tbilisi`, `action`, `result`), в том числе при невозможности продолжать; `no_update` при открытом блокере запрещён. Запись следа выполняется в master отдельным содержательным коммитом состояния, без изменения проверяемого head открытого PR.
- Нельзя: фиктивные PASS, пустые коммиты, handoff/evidence/отчётные файлы, новые тест-файлы (проверки — внутри кода, assert в скриптах).
- `remaining = 0` при `verified < applicable` — это FAIL «fake-complete». Каталог не засчитывает сам себя как интеграцию.
- Не трогать `**/stand/**`, `**/accepted/**`, V5–V7, `reference/sumerek-golden/`, принятые игры. Приватные репозитории — только общее число, без имён, путей и кода.
- В играх: только графика и иконки на экране, всё остальное в меню ☰ справа сверху.
- Нет `gh` — использовать GitHub API/коннектор. Платные API не подключать.
- Уведомлять владельца только ссылкой на проверенную играбельную страницу или при 100%.

## 4. Блокеры и аварийный выход
`workflow.blocker` — единственный источник активного блокера; `blocker_since` — корневой timestamp ISO 8601 Asia/Tbilisi момента установки (null, если блокера нет). Устанавливая или меняя блокер, сохраняй `blocker_since`; снимая блокер, устанавливай null.

При `VERIFY_PENDING` или `VERIFY_FAIL`: :30 исправляет тот же PR, :40 проверяет, :50 сливает только после VERIFY_PASS. Другие стадии обязаны записать выполненное действие или точную причину бездействия в `last_run`, а не `no_update`.
Если блокер старше 3 часов, **ближайший запуск любой из пяти задач независимо от полосы и стадии берёт его на себя**. Для PR: проверь обязательные GitHub Actions на **точном текущем head SHA**; при зелёных основных проверках и отсутствии иных обязательных препятствий запиши технический VERIFY_PASS и слей, при красных исправь в том же PR, при невозможности исправления — закрой PR с зафиксированной причиной. Не объявляй зелёный CI, пока не получен результат на точном SHA. Таймер имеет приоритет над правилом «не более 3 циклов», очередью и запретом новой работы; одновременно второй PR по заблокированному предмету не открывать. В отсутствие инструментов зафиксируй реальную точную недостающую возможность в `last_run.result`, не выдумывай проверку.

## 7. Техническая проверка и CI

:40 сверяет точный текущий SHA PR. Если запустить код негде, **зелёный CI на точном head SHA считается пройденной технической проверкой (VERIFY_PASS)** при отсутствии незакрытых обязательных checks; зафиксировать в `workflow.route.verification` поля `verified_head_sha`, `verified_by: "CI"` и фактические проверки. **Это не вердикт о качестве игры; PASS/FAIL играм ставит только владелец.** Для игр технический CI не заменяет ручную/браузерную проверку настоящего кадра, управления и загрузки и не разрешает выпуск непроверенной графики. Для каталога, если есть независимая проверка GitHub API/деревьев, сохраняй её отдельно и не выдавай CI за проверку всех игровых сценариев. Любой новый кодовый коммит на PR обнуляет прежнюю VERIFY_PASS до проверки нового head SHA.

:50 сливает только совпадающий проверенный head и обязательные зелёные проверки, без ожидания ревью Claude. При красном CI — исправление в том же PR; при отсутствии checks — записать точную причину блокировки. Без новых test, evidence, handoff, отчётных файлов. ## 10. Непропускаемый heartbeat, проверка двух полос и честное завершение

- **Наблюдаемая граница:** `no_update` без `chat_ref` и без `latest_result` означает, что подтверждённого исполнения промпта нет; из этого нельзя выводить «нет задач» или «нет прав». При запуске длительностью около секунды и без связанного чата точная причина до старта агента недоступна в репозитории; требуются журналы самого планировщика/исполнительного окружения. Пять задач не диагностируют отсутствие собственного запуска.
- **Первое действие каждой существующей задачи:** открыть `mpaykin1/World_server:master/architecture/automation-config.md`, `architecture/reuse-state.json` и `mpaykin1/meta6:main/AGENTS.md` через GitHub, проверить права чтения/записи и реальный статус своих PR. Начало работы записать в `last_run` и `run_history` как `STARTED` с `stage`, `lane`, `time_tbilisi`, `action`, идентификатором запуска и исходным SHA; заменить ту же запись результатом `DONE`, `BLOCKED` или `ERROR`, не оставлять `STARTED`. Отсутствие задачи обосновывать результатом `--next` и перечнем PR, а не фразой «нет изменений».
- **Доступ отсутствует:** ошибка GitHub чтения, записи, таймаут, отсутствие инструментов, отсутствие полного промпта или прав — это `ERROR` с именем операции и исходным текстом ошибки. Если запись в GitHub невозможна, прекратить остальные изменения, отправить ошибку в ответ задачи и зафиксировать её на следующем доступном запуске. Нельзя утверждать, что `last_run` записан, если API запись отклонил. Защищённый master не обходить: отдельная рабочая ветка и проверенный PR.
- **Контроль >3 часов:** `node scripts/engines-score.cjs --automation-audit` возвращает `status=RED` и ненулевой код при устаревшем `last_run` (>75 минут), последнем подтверждённом не-RECOVERY запуске (>180 минут), последнем коммите файла состояния/настроек/аудита (>180 минут), неправильной полосе или нарушении видимой работы. Показывать `reason` и `lastTrackedCommit`, не приписывая ручной коммит автоматике. `--automation-audit --record-blocker` дополнительно записывает `workflow.blocker` и `blocker_since` **только в рабочей ветке** с последующим PR; на master запись запрещена. При отсутствии git результат commitAge неизвестен и аудит красный, но это не доказательство отсутствия коммитов на GitHub.
- **Чередование:** нечётный час `Asia/Tbilisi` — `REUSE`, чётный — `IGRY`; все пять стадий одного часа сохраняют полосу. Проверка в `--automation-audit` проходит по каждой записи `run_history` после 03.11.2026. Стадия `RECOVERY` не засчитывается выполненным игровым циклом.
- **Каждый второй выпуск — игра:** две последовательные успешные записи `RELEASE` обязаны содержать хотя бы одну с `lane=IGRY`, `visible_id=visible.*`, `changed_game_files` (пути реальных runtime-файлов из diff соответствующего игрового PR), `verified_head_sha` и merge SHA в `sha`. `--automation-audit` отмечает пару без этих подтверждений как `visibleViolations`; запись `changed_game_files` сверяет :40/:50 с реальным diff на точном HEAD и браузерной проверкой. Каталог и документация не засчитываются.
- **Независимый мониторинг:** этот скрипт не может запуститься самостоятельно при остановке всех пяти задач. Новый GitHub Actions cron или внешний watcher без отдельного решения владельца не создавать. Пока внешняя проверка не одобрена, считать отказы запуска без `chat_ref` непокрытым риском, а не устранённой причиной.
- **Выбор VISIBLE из живого источника:** `scripts/engines-score.cjs --next` без `META6_DIR` не имеет права выдавать непроверенный шаг VISIBLE; нужен checkout `meta6:main` через `META6_DIR` либо чтение runtime-файлов напрямую через GitHub.
