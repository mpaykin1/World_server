# Плейбук: как ИИ самостоятельно развивает игру

Этот процесс применим и к новой игре с нуля. «Готово» определяется не наличием кода, а
воспроизводимым поведением в настоящей игре и человеческой приёмкой.

## 1. Отделить механизм от содержания

- Движок отвечает за физику, кадр, рендер, звук, управление, API реестра.
- Контент-паки описывают врагов, героев, предметы, биомы и их собственные действия.
- Проверять ссылки, допустимые ID и обязательные поля при запуске, а не после публикации.
- Новые генераторы используют независимые потоки случайности. Хэши старых миров — контракт.
- Держать содержательные изменения в отдельной ветке; стабильную ссылку не перезаписывать.

В этом проекте: [реестр](../engine/05_registry.js), [сборка](../tools/build.py),
[контент](CONTENT.md), [графика](STYLE.md).

## 2. Сделать вертикальный срез

Для каждого элемента: схема → реализация → видимый арт → поведение → регрессия → публикация.
Проверки определяются через то, что должен **заметить игрок**, а не через факт вызова функции.

Например, враг «Лунная моль»:

- не только регистрируется и существует в реестре;
- приближается к стоящему герою, реально пересекает его объём и наносит урон;
- после попадания уходит и снова готовится к пике;
- крылья читаются на игровом расстоянии и не скачут при нулевой скорости.

Важно: тест заглушки полезен для изоляции ошибок, но **не заменяет** браузерную проверку.

## 3. Замкнуть цикл в инструментах

Из `games/ostrov-sumerek/`:

```bash
python3 tools/build.py
node tools/test_moonmoth.cjs
python3 tools/check_moonmoth.py
python3 tools/check.py --no-build --bot
python3 tools/bot.py 1337
python3 tools/bot.py --biome frost 1337
python3 tools/shots.py work/shots enemy:moon_moth mobile
```

В корне World_server перед коммитом:

```bash
node scripts/check-js.js
node scripts/check-architecture-limits.cjs
node scripts/check-agent-rules.js
```

После выполнения открыть PNG (в частности `enemy_moon_moth_sheet.png`) и сравнить со
стилем. Если артефакт слабый, исправлять код и повторять полный цикл.

## 4. Не принимать удобные «зелёные» проверки за доказательство

- `node --check` доказывает синтаксис, но не игру.
- Проверка реестра доказывает целостность определений, но не контакт или анимацию.
- Модель физики помогает быстро локализовать дефект; финальное доказательство — реальный
  `window.__isle` в Chromium с измеренными `G.hits`, фазами движения, дистанцией и ошибками.
- Сохранить результат команды, SHA, PNG, обнаруженные дефекты и точный следующий шаг.
- Публикация требует визуальной проверки и проверенной настоящей ссылки; CI alone недостаточно.
- Если не удалось запустить браузер, статус — `NOT_VERIFIED`, а не `PASS`.

## 5. Учиться после результатов, но не присваивать пользовательскую оценку

Каждое подтверждённое замечание превращать в автоматический регрессионный тест.
Историю решения, контрпример и полный тест прикреплять к PR для работы из любого чата.
Только пользователь решает, считать MVP `PASS` или `FAIL`. До этого сохранять
`AWAITING_USER_VERDICT`, не закреплять результат как доказанный успех или провал.
Не объединять в `master` без ревью и явно разрешённой процедуры.
